2. Scalability Analysis

Concurrency Model

The daemon uses a well-structured concurrency model with three distinct lock scopes:

  • D.mu (RWMutex) — protects state, device paths, debounce counters
  • D.cmdMu (Mutex) — serializes mutating commands only; queries bypass
  • streamSema (chan, cap 1) — limits to one MJPEG stream

This is appropriate for a single-device hardware daemon. The read/write lock separation allows concurrent status queries while serializing state mutations.

Scalability limit: Designed for exactly one PIXY device. Not a flaw — this is a hardware daemon.

Dependency Injection

The Dependencies struct consolidates 10 function fields for testability. Production wiring in NewDaemon(), tests override via functional options.

Strong — All external interactions (HID, v4l2, /proc, PipeWire, notifications) are injectable. The two-phase init handles circular refs cleanly.

5. Type Safety

Domain Types

Excellent type discipline throughout:

  • CameraState, AudioMode, AutoMode — string-based with Valid() + String()
  • PID and SourceID — branded types prevent mixing at compile time
  • PTZValues with Clamp() method
  • CommandResult — typed returns for all command handlers
  • CommandError — structured error type with sentinel errors

Strong — Impossible states are largely unrepresentable. The branded ID pattern is particularly well-applied.
