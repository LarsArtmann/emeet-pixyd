07g) The Big Question

Question

Should the PTZ readback goroutine use a coalescing timer instead of one-goroutine-per-set?

ptz.go: schedulePTZReadback

The current implementation spawns a new goroutine for every PTZ set command. Each goroutine waits 500ms then reads back hardware. If a user drags the pan slider rapidly (10+ events in 500ms), we spawn 10+ goroutines that all fire ~simultaneously, each doing a v4l2-ctl --get-ctrl subprocess call. This works correctly (goroutines exit after readback), but it's wasteful — we only need the last position.

The question I can't resolve myself: Should we use a single coalescing timer (reset on each new PTZ set, fire once after 500ms of quiet), or is the current approach actually fine for a hardware daemon that rarely sees rapid-fire PTZ commands? The coalescing approach is more "correct" but adds state management complexity (timer lifecycle, context cancellation). The current approach is simpler and the goroutine cost is negligible for this use case. I lean toward keeping it simple, but I can't determine if there's a real-world scenario where 10 concurrent v4l2-ctl processes would cause device contention or interference.
