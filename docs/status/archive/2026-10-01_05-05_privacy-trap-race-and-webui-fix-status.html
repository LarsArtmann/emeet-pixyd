04d) Totally Fucked Up

Blocking · CI red

Data race makes go test -race ./... fail at HEAD

privacy_trap.go:64 ⟷ privacy_trap_test.go:22

schedulePrivacyTrapReassert spawns a goroutine that reads the package global privacyTrapReassertDelay when it starts; the test helper withShortReassertDelay writes that same global from t.Cleanup. When the goroutine is scheduled after the test returns, the two accesses race. Reproduced at the committed HEAD (not just the working tree): 

WARNING: DATA RACE
Write at ... by withShortReassertDelay.func1()  privacy_trap_test.go:22
Previous read at ... by schedulePrivacyTrapReassert.func1()  privacy_trap.go:64
--- FAIL: TestSetTracking_ReassertSkippedAfterIntentChange (race detected)
Fix Stop mutating a package global for timing. Inject the delay (a Dependencies/clock seam) or gate on the goroutine finishing before cleanup; then re-run the full -race command, not bare go test.

05e) What We Should Improve

Gate on the CI command, not a convenient one

Every "done" claim must be measured with the exact CI invocation (-race, golangci-lint) before it is stated. Bare go test hid this race.

Make timing injectable, not global

Package-level mutable timing vars are a recurring race/test-isolation hazard. Prefer a Dependencies seam or a testClock. Also lets paralleltest re-enable for those tests.

Auto-commit daemon is the systemic risk

Races, unformatted files and undocumented features land because the daemon commits without the full gate. TODO #176 (gate it on a green pre-commit build) is the highest-leverage fix on the board.

Docs-first for hardware-evidenced behavior

The privacy trap is exactly the kind of non-obvious firmware quirk AGENTS.md exists to carry. A CHANGELOG bullet + AGENTS gotcha + FEATURES row should have been part of the same change.

Harvest the audit

Run docs-health HARVEST over the 04-21 report so the 11 findings become tracked task IDs instead of prose.

07g) Top Question I Cannot Answer Myself

Is the privacy-trap re-assert semantics safe to keep as-is, or does it need a product decision?

The mitigation deliberately re-issues the user's mode ~3s later and, for tracking, bounces through idle first (the hardware only recovers that way). I verified the code and the tests, but I cannot decide from inside the repo whether a daemon silently re-writing the camera mode after a click — and briefly passing through idle — is acceptable behavior for users, or whether it should be gated, configurable, or surfaced in the UI. This changes both the feature's contract and how the fix's docs/ADR should read.
